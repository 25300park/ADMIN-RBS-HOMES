## 1. 목표

admin 사이트는 허용된 관리자 계정만 사용할 수 있고, 페이지와 서버 액션 모두 서버에서 세션과 레벨을 확인하며, 로그와 브라우저 응답에 비밀번호 해시와 수신자 이메일이 남지 않는다.

## 2. 범위 안 (할 것)

진행은 두 단계다. **1단계가 끝나면 멈추고 대표 승인을 기다린다.** 승인 없이 2단계로 넘어가지 않는다.

**1단계: 읽기 전용 조사와 계획**
- `middleware.ts`의 레벨 검사(33~36줄 부근)가 주석 처리된 경위를 `git log`와 `git blame`으로 찾아 보고한다 (언제, 어떤 커밋, 이유가 적혀 있는지).
- `actions/` 아래 서버 액션 파일 전체(15개)를 표로 정리한다: 파일, 세션 확인 여부, 레벨 확인 여부, 호출하는 화면. 지금까지 확인된 것은 세션 확인이 없는 파일 8개(banners, dashboard, featured, pms, popup, unit, user, visitors)와 레벨까지 확인하는 파일 3개다.
- 서버 액션 외에 `app/api/**` 등 admin의 다른 서버 진입점(API 라우트, 폼 액션)에도 같은 문제가 있는지 찾는다.
- 현재 admin에 로그인할 수 있는 계정 조건(레벨, `isSuperAdmin`)을 코드로 확인한다. 이 저장소의 정책은 "대표 계정(`isSuperAdmin`)만 접속"이다. 코드가 이와 다르면 차이를 보고하고, 허용 조건 후보를 제시한다. **허용 조건은 대표가 정한다.**
- `app/login/action.ts`와 `app/login/page.tsx`를 확인한다: 비밀번호 확인 전에 사용자 행을 로그로 남기는 줄(14줄 부근), 로그인 성공 시 사용자 객체 전체(해시 포함)를 브라우저로 돌려주는 줄(28줄 부근), 로그인 화면이 이 값에서 실제로 쓰는 필드.
- 수신자 이메일 전체를 출력하는 로그(`actions/message-action.ts`의 361, 452, 568줄 부근)와 원본 오류를 출력하는 로그(`lib/email.ts` 27줄 부근)를 확인한다.
- admin을 안전하게 로컬에서 실행하는 방법을 확인한다. 운영 DB 주소를 쓰지 않고, rbs-homes의 로컬 MySQL(포트 3307)을 쓰는 방법과 보호 장치(운영 DB 접속 차단)가 있는지 보고한다. 없으면 어떻게 만들지 제안한다.
- admin 저장소의 테스트, CI, 브랜치 보호 현황을 보고한다.
- 위 결과와 2단계 수정 계획(파일별 변경 예정, 위험, 되돌리는 방법)을 PR 설명에 쓴다.

**2단계: 대표 승인 후 수정**
- 미들웨어의 레벨 검사를 승인된 허용 조건으로 복원한다.
- 모든 서버 액션과 서버 진입점에서 서버가 세션과 레벨을 확인한다. 한 곳의 공통 함수를 만들어 모든 액션이 같은 방식으로 호출한다 (새 의존성 없음).
- 로그인 흐름에서 해시와 사용자 행을 로그에 남기지 않고, 브라우저로 돌려주는 값에서 비밀번호(해시)를 뺀다. 로그인 화면이 쓰는 필드는 유지한다.
- 수신자 이메일 전체와 원본 오류를 출력하는 로그를 줄이거나 삭제한다 (오류는 이름과 코드만).

## 3. 범위 밖 (하지 말 것)

- 이 브리프에 없는 파일, 화면, 테이블은 고치지 않는다.
- 운영 DB에 접속하지 않는다. `.env*`를 읽거나 수정하지 않는다. 배포하지 않는다 (배포는 대표가 수동으로 한다).
- DB 스키마 변경과 마이그레이션을 하지 않는다.
- 새 의존성을 추가하지 않는다. 테스트 도구가 없어 추가가 필요하면 1단계 보고에 이유와 함께 제안만 한다.
- 인증 방식 자체(NextAuth 구성, 토큰 구조)를 바꾸지 않는다. `NEXTAUTH_SECRET`은 대표가 별도로 교체한다.
- 아래 항목은 다음 브리프로 미룬다: `verifiedById`, admin의 발송 스위치(`EMAIL_MODE`) 도입, `NEXT_PUBLIC_` 접두사가 붙은 AWS와 Gmail 키 이름 정리, `PasswordResetLog` 열 정리, 회원 레벨 변경 이력 기록.
- 계약, 납부, 케어의 쓰기 기능을 만들지 않는다.
- rbs-homes 저장소는 수정하지 않는다.

## 5. 사전 조사 (읽기 전용)

1단계가 곧 사전 조사다. 이미 알려진 사실은 아래와 같다.

- 미들웨어의 레벨 검사가 주석 처리되어, 토큰만 있으면 통과한다.
- 서버 액션 15개 중 8개는 세션 확인이 전혀 없고, 세션의 레벨까지 확인하는 파일은 3개뿐이다.
- rbs-homes에서 2026-09-21부터 2026-11-16까지 데모 로그인 우회가 있었다(수정 완료). 이 기간에는 임의 계정의 토큰이 발급될 수 있었다. front와 admin이 같은 `NEXTAUTH_SECRET`을 쓰면 그 토큰이 admin에서도 통했을 수 있다. 같은 값인지는 코드로 확인할 수 없고, 대표가 두 앱에 서로 다른 새 값을 넣어 해결한다.
- 로그인 액션이 비밀번호 확인 전에 사용자 행 전체(비밀번호 해시 포함)를 서버 로그에 남긴다. 로그인 성공 시에는 사용자 객체 전체를 브라우저로 돌려준다.
